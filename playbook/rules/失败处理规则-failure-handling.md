# 失败处理规则

## 这个文件干什么

任何阶段失败时，不靠感觉跳步骤。先判断失败类型，再回到正确入口。

## 失败类型

| 失败场景 | 回到哪里 | 处理原则 |
|----------|----------|----------|
| 需求问题：目标、边界、术语不清 | [[../prompts/01-需求夯实-grill-me]] | 先问清楚，不写代码 |
| 计划问题：commit 太大、依赖顺序错 | [[../prompts/02-计划拆解-writing-plans]] | 重新拆小，保证可验证 |
| Red 阶段测试没有失败 | [[../prompts/03-TDD实现-tdd-hub]] | 先修测试，让测试能证明缺口 |
| Green 阶段测试失败 | [[../prompts/03-TDD实现-tdd-hub]] | 最小实现，不扩范围 |
| Refactor 后测试失败 | [[../prompts/03-TDD实现-tdd-hub]] | 回退本次重构思路，保持行为不变 |
| Code review 不通过 | [[../prompts/03-TDD实现-tdd-hub]] | 按 review finding 修复，再重新 review |
| Diagnose 验收发现 bug | [[../prompts/03-TDD实现-tdd-hub]] | 先补失败用例，再修实现 |
| Diagnose 验收发现设计不成立 | [[../prompts/01-需求夯实-grill-me]] | 回到需求和边界，不硬补兼容 |
| 线上紧急故障 | [[../prompts/06-紧急修复-hotfix]] | 先复现、定位、最小修复；事后补流程 |
| 当前环境缺少 skill/trigger | [[能力入口索引-skill-entry-index]] | 说明缺失，按 fallback 手动执行 |

## 禁止事项

- 不要在测试红的情况下继续重构。
- 不要因为赶时间跳过最小回归。
- 不要把设计问题伪装成兼容性补丁。
- 不要让写代码的模型独立完成审查结论。

## 输出要求

失败处理结束后，交付说明必须包含：

- 根因一句话
- 修复入口
- 跑过的测试或验收步骤
- 是否需要补文档
